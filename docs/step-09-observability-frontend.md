# 步骤 9（M5）：可观测、评测闭环与前端三页

> 对应 PRD：5.5 前端页面规划（FR-500）、5.7 召回测试（FR-700）、5.8 质量监测与反馈闭环（FR-800）、12 章 M5 里程碑
> 本步完成后：系统从"接口能跑"升级为"质量可量化、问题可闭环、界面可演示"。

---

## 一、本步做了什么（一句话版）

1. **可观测**：给问答全链路装上"仪表盘"——每一步（意图→合规→检索→重排→首字→完成）都有计数和耗时，暴露 Prometheus `/metrics` 和看板接口 `/monitor/summary`。
2. **评测闭环**：建了 116 条评测集（55 中文检索 + 25 跨语言 + 36 合规）和评测 runner（Recall@K / MRR / nDCG / 合规准确率），一条命令跑分、结果存档可对比趋势。
3. **Badcase 闭环**：用户点踩自动生成工单（带完整检索快照）→ 归因 → 一键转评测样本 → 回归，另有 7 日知识缺口榜。
4. **前端三页**：问答（SSE 流式 + 引用卡片 + 反馈）、知识库（上传/版本/分片/OCR 质量）、管理后台（召回测试台/评测/Badcase/合规/SQL/监控），纯静态实现、由后端同进程托管。
5. **演示语料**：`scripts/seed_demo_corpus.py` 一键生成 13 篇多语种文档（中/英/西/阿），评测与前端演示都有"真材实料"。

## 三、关键设计讲解（小白版）

**1. 为什么要自己做指标而不用现成库？**
测试环境没有 Docker/额外依赖。自己实现 ~100 行就能输出标准 Prometheus 文本格式，运维的 Prometheus 直接抓 `/metrics`；以后要换官方 client，接口语义一致。指标是"进程内"的：多副本部署时 Prometheus 会分别抓取再聚合，这是标准做法。

**2. 漏斗怎么看？**
`accepted → intent → compliance → retrieval → rerank → first_token → completed`。
每个阶段记"进入多少 / 成功多少"，例如检索阶段 100 进 99 成，完成率 99%。端到端完成率 = 完成数 ÷（进入数 − 主动中断）。首 Token P95 单独记（PRD 目标 ≤ 3.75s）。

**3. 评测的三个指标是什么意思？**
- **Recall@5（命中率口径）**：前 5 条结果里出现"应该命中的文档"的题目占比。
- **MRR**：正确文档第一次出现位置的倒数（第 1 名记 1 分、第 2 名记 0.5）。
- **nDCG@5**：考虑排序折损，越靠前分越高。
合规集不跑检索，跑的是 precheck：该拦的有没有拦（**红线：漏拦必须为 0**）、不该拦的有没有误拦、提示块有没有附着。

**4. 点踩为什么"即快照"？**
文档会更新、会话会被清理。点踩瞬间把问题、回答、引用原文、检索元数据（通道/耗时/重排/变体）、request_id 全部固化进工单，之后无论数据怎么变，都能复现"当时为什么没答好"。用户撤销点踩时未处理工单自动归档。

**5. 前端为什么是纯静态而不是 React 工程？**
- 演示与验收优先：无需 Node 构建链，`uvicorn` 起来就能用，前后端同源免 CORS。
- 企业内网部署简单：静态文件直接由 Nginx/FastAPI 托管。
- 换 React/Vue 属于 M6 生产化时的"外壳替换"，API 已全部就绪。

**6. RRF 为什么要加权？**
评测揪出的真问题：中文提问时 BM25 会大量命中中文文档，把跨语言语义命中的英文/西语/阿语文档挤出前 5（原 RRF 各通道等权）。修正为向量 1.0 / BM25 0.6——语义为主、关键词为辅（型号/单号仍受益于 BM25，只是不再压过语义）。中文集指标不受影响。

## 四、实测结果

### 1. 自动化测试

```
pytest tests → 112 passed, 1 skipped（新增 12 条 M5 用例：
反馈权限/幂等/快照/状态机/转评测草稿、评测指标与权限、
漏斗与 Prometheus 文本、知识库浏览与隔离、静态前端可达）
```

### 2. 评测跑分（真实模型 bge-m3 + bge-reranker，CPU）

| 数据集 | 条数 | 指标 | 结果 |
| --- | --- | --- | --- |
| retrieval_zh | 55 | hybrid Recall@5 / MRR / nDCG | **100% / 0.979 / 0.996**（向量 98.2%，BM25 100%） |
| retrieval_crosslingual | 25 | **向量通道** Recall@5 | **92%**（跨语言能力的直接体现，≥ PRD 基线 85%） |
| retrieval_crosslingual | 25 | 混合通道 Recall@5 | 76%（加权 RRF 后由 72% → 76%，详见下方"诚实说明"） |
| compliance | 36 | 准确率 / 拦截召回 / 拦截精确率 | **100% / 100% / 100%**，红线漏拦 0，误拦 0 |

**诚实说明（跨语言混合通道低于向量通道）**：演示语料里中/英/西/阿规格书内容互为翻译，中文 BM25 与向量路都会优先命中"中文同款文档"，把外语文档挤出 top5。向量通道 92% 证明跨语言语义匹配本身达标；混合通道的差距是**演示语料重复**放大的，生产语料去重 + 评测集扩到 ≥200 条后应回升。已列入 M6 行动项。

**诚实说明（合规集 100%）**：36 条用例边界清晰（规避操作/制裁国别/知识咨询/普通问题），属于"链路回归集"而非对抗性红队集；生产验收必须用合规负责人标注的 ≥55 条红队集（PRD 11.4）。

### 3. 端到端冒烟（真实服务 + 浏览器）

- 登录 → 提问 → SSE 打字机 → 引用卡片 → 点踩生成工单 → 状态机流转 → 转评测草稿，全链路通过。
- RBAC 模拟：default 用户对"B组价格政策"零召回，biz_b 用户可召回（隔离再次验证）。
- 评测页跑分（合规集 5 条冒烟 ~0.3s）、召回测试台五通道对照、监控漏斗与告警，浏览器控制台 **0 报错**。
- 内存向量库重启后自动重建（启动日志可见 `内存向量库为空，已自动重建索引`），语义检索开箱即用。
- 运行速度：全量 116 条评测（重排候选 10）约 2 分钟，满足"≥100 条 ≤5 分钟"（FR-705）。

## 五、本步修复的问题

1. **误拦截"伪报品名被海关查到会怎样"**：知识咨询语境词表补充"会怎样/有什么影响/严重吗"等句式，合规集准确率 97.2% → 100%。
2. **跨语言混合通道被 BM25 挤压**：RRF 引入通道权重（向量 1.0 / BM25 0.6 / 变体 0.9），crosslingual hybrid 72% → 76%，中文集无损。
3. **降级率指标失真**：未配置翻译模型时 `query_variants` 返回 degraded=False（未尝试 ≠ 失败），否则开发环境降级率恒 100%。
4. **CLI/脚本外键解析失败**（NoReferencedTableError）：`app/models/__init__.py` 集中导入全部模型，任何入口不再漏注册。
5. **内存向量库重启后语义检索静默变空**：预热线程检测到空库自动重建索引。
6. **评测历史表合规集显示 Recall 0%**：合规集无检索指标，前端显示"—"。
7. **聊天页显示 `llm_provider: none`**：未接大模型时显示"未接大模型 · 展示检索依据"。
8. **favicon 404**：内联 SVG 图标。

## 六、已知边界（进入 M6 前必须知道的）

1. **评测集是开发集**：116 条、语料去重不彻底，分数偏高；生产验收需业务标注 ≥200 条（含西/阿各 ≥30 条跨语言）+ 合规红队 ≥55 条。
2. **OCR 仍为同步执行**：上传大扫描件会阻塞请求（PRD 要求 Celery 异步 + 进度轮询，M6 随部署一起做）。
3. **监控为进程内单机版**：多副本需 Prometheus 聚合（`/metrics` 已就绪）；Langfuse trace 未接（PRD M5 列为可选项，接口预留）。
4. **知识缺口榜基于点踩数据**："空答聚类"需要 LLM 归一化 query，暂未实现。
5. **前端为演示级**：未做移动端适配与国际化；会话重命名/删除等 FR-401 细节未实现。
6. **压测未做**：PRD M5 的 80 并发压测需在 M6 部署形态（PostgreSQL + Milvus）下才有意义。
